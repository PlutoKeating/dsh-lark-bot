# v0.19.9 — Self-healing process card

- Fixes #109: the streaming process-card controller no longer treats Feishu's `230011 / "The message was withdrawn"` as a fatal card failure. When a card patch fails because the target message was recalled, replaced or evicted — an ordinary, recoverable condition — the controller now classifies the error, re-creates the card at the conversation tail from the latest snapshot, rebinds the fresh `message_id`, and keeps streaming, instead of freezing the card and posting the alarming "过程卡更新失败" notice.
- Recovery is bounded by `MAX_CARD_WITHDRAW_RECOVERIES` so a hostile loop cannot spawn cards forever; a successful patch resets the budget, so a long-running card stays usable. Only genuinely unrecoverable failures (network/timeout after the limited retries) degrade to a static card with the fallback notice — the running agent and the final Markdown answer are never interrupted.
- This closes the gap left by #106, which had serialized concurrent re-anchors but did not add recovery for an already-withdrawn message (the failure reproduced on 0.19.7 in `service.log`: `lark-card-stream patch-disabled`, Feishu `230011`).
- Adds regression tests: a single withdrawal self-heals to a fresh card, and repeated withdrawals converge after the recovery budget instead of looping.
- Verified against the full local test suite (146 files / 806 tests), typecheck, build, and the TUI admission/PTY and publish-bundle gates.
